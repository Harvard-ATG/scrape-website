The 5-Minute Version

APO Bot is a Harvard AI assistant backed by 100-200 scraped websites in an OpenAI vector store. Students ask questions, the model retrieves relevant chunks, and generates cited answers.

The problem: citations don’t link back to source pages.

How it works today

When a student asks a question:

  1. Query pre-processing: Platform reads agent config from DynamoDB, builds tools array + system prompt
  2. Platform calls Responses API: client.responses.create() with prompt + citations prompt + File-Search Tool + include=["file_search_call.results"]
  3. Tool: File-Search (server-side): Embeds the query → searches the vector store → ranks results → injects top chunks into model context
  4. Model generates: Uses top chunks returned from vector store to write answer, builds a reference list, and emits PUA citation markers (V2 is now default, runs unconditionally)
  5. Response post-processing: Processes model response, builds inline citations and matching Sources panel

The gap

The platform now returns search_results with each response and joins them to annotations by file_id — but there’s nothing to join to. The vector store supports custom attributes per file (like origin_url), but nobody is setting them at upload time. The join works; the data is empty.

The fix (only remaining step)

Goal: Hydrate custom attributes (origin_url, domain, title) on every file in the vector store at upload time. Once set, the existing platform code picks them up automatically.

Why not just read the file content?

  • ✓ Scraped .md files: Could parse YAML frontmatter for origin_url, domain, title — this works
  • ✗ PDFs, Word docs, other formats: No frontmatter, no header to parse — content doesn’t carry metadata
  • Therefore: Reading file content only covers one file type. We need a solution that works for all.
HA Platform-Based Solution: Hydrate Attributes Using manifest.json
  1. Scraper produces manifest.json: A single mapping file (filename → origin_url + domain + title) that covers ALL file types regardless of format
  2. sync_engine.py reads manifest at sync start: Looks up attributes per file, merges into the attribute dict before upload
  3. Done: The existing include + join_file_search_results() picks up the attributes automatically — citations get URLs with zero additional code

🎉 Every citation gets a clickable URL. Zero extra API calls. Zero latency cost. Platform code is already in place.

What’s blocking

Blocker 1: Attribute Hydration Need manifest.json (filename → origin_url + domain + title) and a small change to sync_engine.py to read it and merge into attributes at upload. See suggested fix →
Blocker 2: S3 Sync FileSync needs AWS IAM credentials. Need role setup or alternative integration path from Ventz.
✓ Platform code include param (chat_send_message.py:938) and join_file_search_results() (citations.py:412) are already live. No PR needed.
Alternative Pathway — Exploratory

MCP Experiment: Entirely separate process outside of the HA platform logic — the response would be handled in its own black box, independent of FileSync, vector store attributes, and the existing citation pipeline. Currently in exploratory phase; not yet defined. The HA Platform-Based Solution is to hydrate attributes using manifest.json (above).

3. Scraper — Issues & Open Questions

We forked the scraper — it's ours to modify. The core engine works. This section maps the issues by category and connects them to downstream concerns (platform preprocessing, citation quality, S3 delivery).

A. Access & Concurrency (Solved — With Implications)

Win: Concurrency = 1 Eliminates All 503 Errors

Jeremy tested against aaas.fas.harvard.edu (2,037 URLs discovered, 1,757 pages fetched). Dropping concurrency from 100 to 1 completely eliminates Harvard CDN rate limiting.

BEFORE: CONCURRENCY = 100
~3 min, 503 errors across the board
AFTER: CONCURRENCY = 1
16.8 min, 0 errors

Result: The scraper works reliably. We have a clean, error-free crawl path.

Implications of the Win

16.8 min for one site. At 100-200 sites with hundreds to thousands of pages each, a full corpus run is days, not hours.

MVP: Acceptable. Run it, wait, done. One-time initial scrape.
Refinement: Can't afford full re-runs regularly. Need to only re-scrape pages that changed, only upload files that are new/different, only sync what's actually new to S3.
Tweaking: Room between 1 and 100. Adaptive backoff (10-20?) might find a sweet spot — faster without triggering 503s.

This drives the need for diff detection at every stage (see Category C below) and smart use of the database layer (see Jeremy's architecture in Section 4).

Known: 401/403 HKey-Protected Pages

266 pages across 3 test sites returned 401/403 — login-protected behind Harvard Key. Not a scraper bug; these pages are inaccessible without credentials. Logged to access_denied.txt.

B. Scoping Issues

Domain-Level Scoping Only (No Path Filtering)

Passing https://math.harvard.edu/undergraduate sets base_domain = "math.harvard.edu" and crawls the entire domain — not just pages under /undergraduate. The --no-crawl flag is the only blunt instrument (follow all links or none).

Planned but not built: --max-pages N flag and path_prefix filtering. sites.yaml already defines path_prefix for some sites, but the scraper ignores it.

~80% of Department Pages Are Events/People/News

Full crawl of aaas.fas.harvard.edu: 1,757 pages — 862 news, 624 events, 153 people. Only ~180 pages are "core" academic content.

Brooks confirmed: Events, people, and news content IS needed. Path exclusion is NOT the right strategy. The bot should have department event info and faculty details.

Cross-Page Deduplication Removes Content

Trafilatura deduplicates text across pages within a domain. If the same passage appears on an FAQ page and a standalone page, it gets removed from one. Pages with only duplicate text produce no output file at all.

Fix: Set deduplicate=False. Question: Any reason to keep cross-page dedup for a knowledge base?

C. Diff Detection (Cross-Cutting — Same Problem at Every Stage)

With full runs taking days, we need to know what changed without re-running everything. The same question appears at three stages, each with different costs:

Stage Question Current State Cost of Not Having It
1. Scraper "Has this page changed since last run?" No content diffing. Either skip (resume) or re-scrape everything (fresh). Re-fetching tens of thousands of unchanged pages. Hours of runtime wasted.
2. S3 Upload "Is this file already in S3 and unchanged?" No check before PUT. Uploads everything every time. Unnecessary S3 PUT requests (cost $$$). Also: S3 reads cost money — checking "what's already there?" by listing/reading from S3 is itself expensive at scale.
3. FileSync "Is this S3 object new/changed vs. what's in vector store?" Solved. ETag/hash comparison built in. Already handled — but it still has to read from S3 to compare. If we upload unchanged files, FileSync does unnecessary work.

The Database Layer Solves This (Jeremy's Architecture)

A local DB (SQLite or similar) that stores: URL, content hash, timestamp, S3 key, filename. Enables:

  • Scraper stage: "I last scraped this URL on date X with hash Y. Re-fetch and compare hash — if same, skip extraction/upload."
  • S3 stage: "I know the filename and hash for this content. DB says S3 already has this exact file. Don't PUT."
  • Manifest: DB is the authoritative URL → filename → S3 key mapping. Generate manifest.json from it.

E. Delivery to S3 & FileSync

Getting scraper output into S3 in a way that FileSync can efficiently process. Two layers of hash-based change detection mean unchanged pages cost effectively zero. The scraper-side decisions that matter:

Why Single-Part PUT to S3 Matters

FileSync uses ETags for change detection across all adapter paths (S3, SharePoint, Google Drive). Multi-part uploads produce composite ETags ("d41d8cd9...-3") that are a hash of concatenated part hashes — dependent on part size, NOT content. Same file uploaded twice with different part sizes → different ETags → FileSync sees "changed" → unnecessary delete + re-upload to vector store.

"boto3's upload_file() uses multipart upload for files > 8MB (configurable via multipart_threshold). Multipart ETags look like: "d41d8cd9...-3" ← composite hash, NOT content MD5. This ETag is a hash of the concatenated part hashes, dependent on part SIZE (which can vary), NOT deterministic across separate uploads of identical content with different chunking."
— 04_storage_and_sync_decisions.md § 5
"Only FileSync tracks state and compares hashes. The Wizard and Admin UI are stateless — they upload to OpenAI and attach to the vector store with no awareness of what already exists. This is why the FileSync/S3 path is the correct automated pipeline: it is the only path with built-in change management."
— meeting_huddle_2026-05-06.md
"FileSync on the platform side handles change detection via ETags/hashes — so the delta problem may be better solved at the sync layer than the scraper layer."
— meeting_huddle_2026-05-06.md — Delta Identification

AWS Documentation

Compare local content hash to S3 ETag (HeadObject)
Match → skip upload (save bandwidth)
Differ → upload new content
LAYER 2: S3 → Vector Store (FileSync)
Compare S3 ETag to stored file_hash in state DB
Match → skip (save OpenAI API + embedding cost)
Differ → delete old vector file, upload new, re-embed

7. How Chunking Works

When a file is uploaded to the OpenAI vector store, it gets split into overlapping segments called chunks. Each chunk is independently searchable — when a student asks a question, file_search returns the most relevant chunks, not whole files.

Key Rule
Chunk size (800 tokens) is a MAX — not a target.

A file under 800 tokens is never split, regardless of how much whitespace it contains. Whitespace is the preferred split point when a split is needed — it is not a split trigger.

Default Settings (APO Bot)

Parameter Value What It Means
max_chunk_size_tokens 800 Maximum tokens per chunk. Never exceeded.
chunk_overlap_tokens 400 Each chunk shares its last 400 tokens with the next chunk's beginning.
chunking_strategy static (default) Splits at whitespace/paragraph boundaries. No semantic analysis.
Not configured in our code The platform calls client.vector_stores.create(name=vs_name) with no chunking_strategy parameter — it uses OpenAI's defaults. Changing this would be a one-line addition.

How Overlap Works

Overlap ensures continuity between chunks. The last 400 tokens of chunk N are repeated at the start of chunk N+1. This means adjacent chunks share context — and critically, if metadata is in the first ~40 tokens of the file, the overlap carries it into chunk 2.

11. Citation Layers & The V2 Pipeline

✓ Updated: V2 is now the platform default. The env flag and V1 fallback have been removed. V2 runs unconditionally for all agents.

A response contains three types of citations:

  1. Inline citations — [1], [2] markers within the response text (platform-driven, from invisible PUA markers)
  2. Sources panel — numbered list alongside the response showing filename, block locator, and URL if available. Order matches the inline citations. (platform-driven)
  3. References list — ### References section at the end of the message body (model-driven, from system prompt instructions)

There are two mechanisms that produce these citations:

  1. V2 platform pipeline — preprocessor + PUA markers + post-processor. Creates inline citations (#1) and the Sources panel (#2).
  2. Core system instruction prompt — instructions configured by admin that tell the model to build a references section. Creates the References list (#3).

The V2 Pipeline (Now Default)

Component Status Controls What It Does
CITATIONS_V2_PREPROCESS ON Upload / Ingestion Stamps [Block<n>] markers into file content before uploading to vector store
V2 Post-processor ON (unconditional) Prompt + Post-processing Appends PUA citation instructions to system prompt and parses PUA markers into [N] + Sources panel

What V2 Does

Preprocessing (upload):

  • A file gets uploaded from S3
  • Before it enters the vector store, the preprocessor splits it on every blank line
  • Each section gets stamped with a [Block<n>] marker (PDFs get [P<n> Block<m>] for page + block)
  • Markers survive chunking because they ride with the text
  • When a chunk is retrieved later, the model can reference exactly which block it came from

System prompt:

  • The core system instruction prompt already has a section about citations and how to build a ### References section
  • Citations V2 adds a tiny citations prompt on the tail end of the core system instruction prompt + query — tells the model how to emit invisible citation markers (used to create the inline citations and the Sources panel)
  • What the model returns: the response text with invisible citation markers embedded + a references list

Post-processing:

  1. Parses PUA markers the model emitted
  2. Resolves source IDs against annotations (file_citation + url_citation)
  3. Joins annotations to search_results by file_id (join_file_search_results())
  4. Strips all PUA characters from visible output
  5. Returns typed citation schema (filename, locator, quote, url — url populated if attributes are set)
  6. Frontend renders Sources panel with block locators

Regardless of the V2 pipeline, the core system instruction prompt (configured by the admin in the UI) independently instructs the model to generate its own references. This is completely separate from the platform machinery.

    """Enrich `ann_files` in place with chunk text/score/attributes.

    OpenAI Responses `file_citation` annotations carry only file_id/filename/
    index — NO quote text. The grounding excerpt, relevance score, and file
    attributes are only available when the response was requested with
    `include=["file_search_call.results"]`; they arrive as a separate list
    keyed by file_id (one entry per retrieved chunk, possibly several per
    file). We join by file_id and keep the highest-scoring chunk per file as
    the representative quote.
    """
    if not file_search_results or not ann_files:
        return ann_files

    best_by_fid = {}  # file_id -> (score, text, attributes)
    for r in file_search_results:
        fid = _fsr_get(r, "file_id")
        if not fid:
            continue
        score = _fsr_get(r, "score")
        text = _fsr_get(r, "text") or ""
        attrs = _fsr_get(r, "attributes")
        prev = best_by_fid.get(fid)
        # Keep the highest-scoring chunk (None score sorts lowest).
        if prev is None or (score or -1) > (prev[0] or -1):

        ann["score"] = score                        # ← bonus
        ann["attributes"] = attrs                  # ← bonus (along for the ride)
    return ann_files

Where Does manifest.json Come From?

The scraper already maintains a SQLite database (URLStore) for URL dedup tracking. This DB has the filename ↔ source URL mapping as a byproduct of crawling. Three options for producing the manifest:

A. Generate from scraper DB after crawl

At end of crawl, query the SQLite DB and emit manifest.json to the output directory. Upload to S3 alongside content files.

Pro: DB is authoritative source of truth; manifest is a derived artifact, always consistent.
Con: Requires scraper modification (minor — one query + json.dump at end of run).

B. Build on-the-fly during scrape

As each page is saved, append its entry to the manifest dict in memory. Write once at end.

Pro: No extra DB query step; manifest stays perfectly in sync with output files.
Con: Slightly tighter coupling; if scraper crashes mid-run, partial manifest.

C. Skip manifest — expose the DB directly

Make the scraper DB (DynamoDB/Postgres/SQLite) queryable by the platform at sync time instead of a flat file.

Pro: Always fresh; no stale file risk.
Con: Cross-service coupling; DB calls per file during sync; network latency; access control.

Where Does It Live?

S3 (alongside content) ✓

FileSync already has S3 access. Manifest is loaded once at sync start, held in memory. Versioned via S3 versioning. No new infrastructure.

DynamoDB table

New table (PK=filename). Platform queries per-file or scans at sync start. Adds infra; requires provisioning + IAM.

Postgres / shared DB

Full relational store. Handles 80K–100K rows easily, but adds operational burden (RDS ~$15–30/mo, migrations, connection pooling, VPC). Justified only if already running Postgres elsewhere.

Why manifest.json Wins

Advantages

  • Loaded into memory once — single S3 GET at sync start; no per-file DB calls
  • Versioned in S3 — full history, rollback trivial
  • Debuggable — open in any editor, jq '.files["advising.md"]' manifest.json
  • Portable — no infrastructure coupling; works with any consumer
  • No cross-service auth — same S3 bucket, same IAM role
  • Consistency gate built-in — generated_at timestamp lets FileSync skip mid-crawl uploads without blocking the entire sync

Downsides (in practice)

  • Export step required — if the scraper runs but the export fails or is skipped, manifest goes stale; must be wired into end-of-crawl reliably
  • Mid-crawl window — files uploaded to S3 before manifest re-export are invisible to FileSync (by design — generated_at gate holds them back until next export confirms them)
  • Scale ceiling — at 80K–100K files, single JSON blob is ~12MB; loads in <1s but grows linearly with fleet
  • Full dump each sync — cheap (SELECT → json.dumps ~160ms for 80K rows) but still a full export vs. DB row upsert for 5 changed pages
  • No query semantics — can't ask "which files have domain=X" without loading + filtering; operator uses the SQLite DB for ad-hoc queries instead

Scale context: 80–200 sites × ~400 pages each = 32K–80K files (~12MB manifest). Still loads into memory in <1s via single S3 GET. The scraper DB (SQLite) is the source of truth; manifest.json is the sync-time export — rebuilt once before FileSync runs, not after every partial crawl. Concurrent/incremental crawls upsert rows in the DB independently; the manifest is derived. Consistency: generated_at timestamp in the manifest lets FileSync skip S3 files with LastModified > generated_at (mid-crawl uploads not yet confirmed by a fresh export). No sentinel files, no locking — just a free timestamp comparison using data S3 already provides. See scrape-website/context/manifest_storage_analysis.md for full storage options comparison.

def build_references_section(citations: List[Dict]) -> str:
    """Build a ### References block from resolved citation objects.

    if not citations:

        else:
            lines.append(f"[{num}] {title}")

    return "\n".join(lines)

15. Manifest & State DB

The manifest.json is the authoritative mapping of every file in the vector store back to its source. Each entry maps a filename (the key) to its origin_url, domain, title, and — for binary files — found_on (the page that linked to the download).

Why it exists: binary files (PDFs, DOCX, XLSX) can’t hold metadata internally. Even for web pages where frontmatter contains the source URL, that metadata gets chunked away from the citing chunk in large files. The manifest is the universal source of truth regardless of file type — it’s what the citation pipeline reads from at upload time.

Filenames must be unique — they’re the manifest key. If two files share a filename, one overwrites the other in the manifest and becomes invisible to sync. The filename convention guarantees uniqueness via an 8-character URL hash suffix. → See §16: Filename Convention for the full design.
Filenames are stable — they never change when page content updates. The filename is derived from the URL (which is permanent), not from page content. This means the manifest key for a given page is the same across every crawl. Content changes trigger a content_hash update (for change detection), but the filename — and therefore the manifest entry — stays put.

The Dump: Why JSON on S3 (Not Direct DB Access)

Design Principle
The boundary between scraper and platform is S3. The manifest.json is the contract artifact at that boundary.

The platform should never need a live connection back to the scraper’s local database. They communicate through files in S3 — decoupled, inspectable, store-agnostic.

Why Dump (Not Direct Read)

  1. Decoupled: Scraper runs, dumps, pushes to S3. Platform reads whenever it syncs. They don’t need to be online simultaneously.
  2. Store-agnostic: Whether the backing store is SQLite (now) or Postgres (MCP route later) — the contract doesn’t change. It’s always flat JSON in S3.
  3. Debuggable: Anyone with aws s3 cp + jq can inspect the manifest. No DB credentials, no SSH tunneling, no query tooling needed.
  4. No cross-service auth: Same S3 bucket, same IAM role that FileSync already uses. No new permissions to provision.
  5. Atomic & versionable: One file, versioned in S3. Rollback to a previous manifest is a single CLI command.

import json, sqlite3
from datetime import datetime, timezone

def export_manifest(db_path: str, output_path: str) -> int:
    """Export manifest.json from the scraper state DB.

    Reads all files_metadata rows and writes a JSON mapping of
    filename → {origin_url, domain, title, found_on?} to output_path.
    Includes generated_at timestamp used by FileSync as a consistency gate.

    Returns the number of entries written.
    """
    conn = sqlite3.connect(db_path)
    rows = conn.execute("""
        SELECT filename, url AS origin_url, domain, title, found_on
        FROM files_metadata
    """).fetchall()
    conn.close()

    files = {}
    for filename, origin_url, domain, title, found_on in rows:
        entry = {
            "origin_url": origin_url,
            "domain": domain,
            "title": title,
        }
        if found_on:  # only for binary files
            entry["found_on"] = found_on
        files[filename] = entry

    manifest = {
        "generated_at": datetime.now(timezone.utc).isoformat(),
        "files": files,
    }

    with open(output_path, 'w') as f:
        json.dump(manifest, f, indent=2)

    return len(files)

16. Filename Convention (The Key)

The filename is a lookup key — it must be unique and deterministic. It doesn’t need to be perfectly human-readable or discernible at a glance; the manifest has the full URL and title for anyone debugging. The hash suffix guarantees uniqueness. Everything else is best-effort context.

The Problem: Why Counters Break

The current scraper uses generate_html_filename() which derives the filename from the URL path only (/advising → advising.md). When two domains have the same path, it appends a collision counter: _1, _2, etc. The counter depends on crawl order — which is non-deterministic.

First Crawl (german before math)

german’s /advising → advising.md
math’s /advising → advising_1.md

Second Crawl (math before german)

math’s /advising → advising.md
german’s /advising → advising_1.md

Result: manifest key advising.md now points to a different URL. FileSync sees the wrong metadata. Citations link to the wrong page.

The Convention

Every URL is mechanically converted into a flat filename. The function is pure — given the same URL, it always produces the same filename regardless of crawl order, timing, or machine state. No database lookup, no collision counter, no disk check.

URL:  https://german.fas.harvard.edu/advising/undergraduate-requirements

Pattern: {domain}__{path-slug}_{url_hash8}.{ext}
File: german_fas_harvard_edu__advising_undergraduate-requirements_a7b3c9e4.md
     |_____________________|__|_________________________________|_|_______|__|
           domain (22)      ^^      path slug (35)                 hash(8) ext
                         separator
Deterministic

f(url) → filename — no state, no counter, no disk check. Same URL always produces the same filename on any machine, any run.

Stable

URL-based, not content-based. Page content changes → filename stays the same. Manifest key is permanent.

Unique

URLs are already globally unique — no two can resolve to the same place. The URL is the identity.

Why the Hash? Truncation Collision Insurance

Every URL is already unique — we don’t need a hash for identity. But when we truncate long URLs to fit a character budget, two different URLs could theoretically produce the same truncated slug. The 8-char hash (md5(full_url)[:8]) makes collisions mathematically impossible (~1 in 4 billion) regardless of how aggressive the truncation is.

We include the hash when these are true:

  • The filename exceeds or approaches the character budget (truncation needed)
  • Multiple pages share long common prefixes (e.g. event-heavy sites with similar titles)
  • The distinguishing part of the URL is past the truncation cut point
  • We want one universal filename function — no conditional logic for "short enough" vs. "needs hash"

At 200 chars: hash is near-zero probability of ever being needed

  • Two URLs would need identical first ~165 chars of path to collide — effectively impossible
  • Filenames are nearly self-documenting (full URL path visible)
  • Hash is still there as insurance — costs nothing functionally, just 9 chars of width

Decision: We include the hash unconditionally in all filenames. It’s cheap insurance (9 chars), keeps the filename function simple (no branching for "needs hash" vs. "doesn’t"), and makes the system provably collision-free at any truncation length. The manifest provides the reverse lookup (filename → URL) that the hash intentionally makes impossible.

Rule of thumb: If you see a hyphen in the filename, it was already a hyphen in the URL or came from a space in the original doc name. If you see an underscore, we put it there (replaced a dot, slash, or used it as the hash separator). Double underscore __ always means "domain ends here, path starts here." Special characters (&, @, etc.) are stripped. Truncation only sacrifices the path slug — domain, hash, and extension are never touched.

We expect truncation to rarely trigger. Most Harvard URLs produce filenames well under 100 characters. Bottom line: Truncation has zero functional impact on the pipeline. The only cost is human readability in two places (Sources panel, debug logs) — and both have the full URL available via manifest or attributes. We truncate as a caution against future system additions that might have tighter limits, and to keep filenames manageable for anyone touching S3 directly.

TL;DR

  • The filename passes through every system in the pipeline. None of them break at 120 — or even 200.
  • The question is where readability degrades vs. how much URL context we preserve.
  • We truncate as a defensive choice, not because anything fails today.
  • The hash guarantees uniqueness regardless of truncation length.
  • The manifest has the full URL for anything lost to truncation.

  • Two-line wrap in narrow terminals

from hashlib import md5
from urllib.parse import urlparse

def generate_filename_web(url, max_len=120):
    """Deterministic filename from a web page URL."""
    parsed = urlparse(url)
    domain_slug = parsed.hostname.replace('.', '_')
    path = parsed.path.strip('/')
    path_slug = path.replace('/', '_') if path else 'index'
    h = md5(url.encode()).hexdigest()[:8]
    suffix = f'_{h}.md'

    candidate = f'{domain_slug}__{path_slug}{suffix}'
    if len(candidate) <= max_len:
        return candidate  # fits — use full path

    # Truncation: fill budget with path from left, cut at word boundary
    budget = max_len - len(domain_slug) - 2 - len(suffix)
    truncated = path_slug[:budget]
    if '-' in truncated and len(truncated) < len(path_slug):
        last_hyphen = truncated.rfind('-')
        if last_hyphen > budget * 0.7:
            truncated = truncated[:last_hyphen]
    return f'{domain_slug}__{truncated}{suffix}'

import os

def generate_filename_binary(url, original_filename, max_len=120):
    """Deterministic filename from a binary file's download URL + original name."""
    parsed = urlparse(url)
    domain_slug = parsed.hostname.replace('.', '_')
    h = md5(url.encode()).hexdigest()[:8]
    name, ext = os.path.splitext(original_filename)
    name = name.replace(' ', '-').lower()
    suffix = f'_{h}{ext}'

    candidate = f'{domain_slug}__{name}{suffix}'
    if len(candidate) <= max_len:
        return candidate  # fits — use full original name

    # Truncation: keep head + tail (binary names are descriptive throughout)
    budget = max_len - len(domain_slug) - 2 - len(suffix)
    segments = name.replace('-', '_').split('_')
    if len(segments) >= 4:
        head = '_'.join(segments[:2])
        tail = '_'.join(segments[-2:])
        middle_marker = '_.._'
        if len(head) + len(middle_marker) + len(tail) <= budget:
            truncated = f'{head}{middle_marker}{tail}'
        else:
            truncated = name[:budget]
    else:
        truncated = name[:budget]
    return f'{domain_slug}__{truncated}{suffix}'
